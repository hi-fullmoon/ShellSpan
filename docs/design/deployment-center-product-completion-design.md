## 1. 产品目标与范围

用户提供本地项目、目标服务器和部署目录后，能够完成首次接入、发布更新、确认服务状态和恢复版本。默认路径不要求用户理解节点、端口绑定、产物摘要或调度器。

推荐采用“应用 + 环境 + 发布”的产品入口，保留现有工作流作为执行定义和高级编辑入口。模板、引导表单和高级编辑器最终操作同一份工作流，不引入第二套发布引擎。

第一期完整交付本地 Git 项目到单台 Linux 主机的 Docker Compose 部署；保留已有静态站点能力并纳入相同应用入口。一个应用可以配置多个环境，但一次发布仅作用于一个环境、一台主机。首个默认环境为“生产”，不自动创建测试环境。

第一期不承诺零停机，不加入 Kubernetes、自动 CI 触发、远端源码构建、多机滚动更新或任意 Shell 节点。已有自定义工作流继续可见、可管理。

## 3. 信息架构

部署中心保留一个入口，左侧显示应用列表，右侧显示选中应用的环境和详情。列表展示名称、环境、最近发布结果及待处理事项，不把“最近一次发布失败”直接等同于“服务不可用”。

应用详情提供四个页签：

| 页签 | 核心内容 | 主要操作 |
| --- | --- | --- |
| 概览 | 主机、目录、访问地址、当前版本、最近检查、接入问题、当前运行 | 检查环境 / 准备发布 / 查看进行中的发布 |
| 发布记录 | 发布时间、源码版本、操作者或触发来源、结果、恢复结果 | 查看详情、重新准备 |
| 版本 | 当前版本、上一版本、可恢复版本、产物是否可用 | 查看版本、准备回退 |
| 配置 | 项目、环境、构建、数据、健康检查、保留策略 | 保存配置、打开工作流编辑器 |

“准备发布”是有独立运行身份的详情视图，从概览或历史记录进入，支持返回后继续查看，不再要求用户先切换到设计页。

全局“运行”入口可以筛选全部应用的运行；产物仍以版本或运行详情 Drawer 展示。第一期不增加独立产物管理主页。

默认不加载无限画布。高级编辑器复用当前设计页，保留节点库、校验、布局和键盘操作。仅部署中心内新增这些入口，不改动其他工作台页面。

## 4. 接入应用：四步引导

引导采用正文分区与固定操作栏，支持保存草稿和返回上一步。每步展示明确问题与修复入口；未通过检查可保存草稿，不能准备正式发布。

### 第一步：选择项目

- 输入应用名称，使用系统目录选择器选择本地 Git 根目录。
- 显示规范化路径、仓库身份、当前分支、提交和工作区改动数量。
- 检测 package.json、锁文件、Dockerfile、Compose、静态构建配置，给出带依据的部署方式建议。
- 检测结果不是不可更改的判定；用户可选择兼容模板，冲突时解释阻塞原因。
- Docker 配置已存在时读取并选择服务；缺失时提供“生成部署文件”操作，先展示文件内容和差异，再明确应用到项目。
- 不覆盖已有文件；不自动提交 Git；不把 node_modules、构建缓存、数据或凭据带入源码产物。
- 首期允许发布包含未提交改动的明确快照，在准备页展示范围；未跟踪文件必须列出并明确纳入，受忽略的文件不自动收集。

### 第二步：配置环境

- 环境名称默认为“生产”，选择现有 SSH 连接，填写远端绝对目录。
- 选择或检测平台架构；本地构建平台必须与目标一致。
- 填写 Compose 项目名和目标服务、对外访问地址、容器端口、宿主机绑定地址和端口。
- 生产模板默认将应用端口绑定到回环地址，由既有代理提供入口。
- 访问地址、服务器文件目录和应用 basePath 独立保存；更改目录不能推导或重写访问路径。
- 密码、密钥和 token 只保存 credential reference；环境展示读取权限和用途，不展示值。

### 第三步：数据与首次接入

- 为每个可写目录配置宿主机路径、容器路径、读写方式、容器运行用户和备份策略。
- 持久化目录固定于 shared 下或显式登记的外部路径，不跟随版本目录变化。
- 检查已有服务、端口占用、现有目录内容和部署中心所有权标记，判断“新部署”或“接管现有服务”。
- 未知进程占用端口时不自动停止；用户可以调整端口并重新检查。
- 对已在运行的服务记录管理方式、启动配置、数据位置和恢复方法。首期不自动接管未知进程管理器。
- 需要数据迁移时显示单独的接管清单：备份、暂停写入、最终同步、校验、切换和失败恢复。缺少恢复方案不得宣称可自动回退。

### 第四步：检查与保存

检查本地 Docker/Buildx、源码与锁文件、目标 SSH 身份、SFTP、Docker/Compose、架构、端口、磁盘空间、目录权限和代理入口。每项显示“通过 / 阻塞 / 提示 / 未检查”、检查时间和可执行的下一步。

读检查不安装软件、不创建远端目录、不重载服务。缺目录时可以单独准备“初始化目录”计划，显示路径、权限和预期影响，确认后执行；它具有独立审计记录和精确计划绑定。不要为了初始化放宽日常发布审批。

第一期由用户在现有终端完成 Docker 安装和未知服务迁移，界面持续保留问题和复查入口。创建目录、应用专属代理配置等后续自动化只能使用类型化固定动作，不能增加任意脚本执行入口。

保存后进入应用概览，显示“接入未完成”或“可准备发布”。环境检查通过仅表示准备条件满足，不代表服务已上线。

## 5. 正常发布流程

用户主路径为：选择应用与环境、准备发布、核对发布内容、确认发布、查看结果。

| 阶段 | 后台行为 | 用户看到的内容 |
| --- | --- | --- |
| 准备 | 冻结源码和配置，快速检查目标能力，再构建并生成发布产物 | 构建阶段、耗时、错误、可取消操作 |
| 最终预检 | 复核目标身份、占用、现行版本、空间及恢复条件 | 阻塞项或可审批候选版本 |
| 待确认 | 冻结完整计划和有效期 | 发布什么、发布到哪里、影响、验证、恢复方式 |
| 执行 | 锁定目标资源，上传、校验、加载镜像、更新服务 | 当前步骤、上传字节、日志和取消状态 |
| 验证 | 有界等待就绪，执行必需检查 | 每项检查结果及失败原因 |
| 完成 | 验证通过才记录当前版本 | 新版本、访问入口、验证时间 |

准备期间允许有界本地构建，但不执行远端写入或服务变更。构建可能执行项目构建逻辑，其授权由“准备发布”的说明明确表达；项目检测本身不执行依赖脚本。

审批页必须展示源码提交与改动、目标主机和目录、服务及端口、镜像和配置变更、数据挂载变化、预计短暂中断、全部健康检查、旧版本与恢复限制。摘要作为可展开技术详情，不要求用户核对长哈希。

配置、目标身份或前置现行版本变化会使计划失效；布局变化不失效。已冻结并物化的源码不受之后编辑文件影响，界面提示存在较新改动，但不能悄悄替换候选版本。计划过期需要重新准备；可复用已验证且受保留保护的产物，不必无条件重建。

同一服务器身份下重叠部署根目录、相同 Compose 项目或冲突宿主机端口必须互斥，不仅按环境 ID 加锁。存在状态待确认的副作用时阻止冲突运行。

## 6. 源码和 Compose 产物闭环

### 源码绑定

应用记录本地 source binding；运行冻结 binding revision、仓库身份、内容摘要和源码快照。原生执行器从运行上下文读取明确路径，禁止回退到进程 current_dir。

选择目录后通过规范化、Git 根目录验证和文件边界检查。目录丢失时提供重新定位，验证仓库身份；重新定位不能重写历史运行的来源。

构建只读取冻结快照物化的隔离目录。Docker 构建上下文、Dockerfile、锁文件及 Compose 都必须从同一快照读取，防止检查后文件变化产生混合版本。

### 发布专用 Compose

使用成熟 YAML 解析依赖以及 Docker Compose 官方 CLI 进行配置解析与验证，不使用正则或字符串替换 YAML。

1. 从冻结源码加载所选 Compose 配置，明确多个文件的合并顺序和允许的变量来源。
2. 将指定服务 image 绑定到本次镜像归档中的准确版本引用，记录 image ID 与归档摘要；第一期只支持一个受管应用镜像，其他服务使用明确固定镜像身份或阻止发布。
3. 生成发布专用配置，移除受管服务的构建路径，执行时禁止远端构建，默认不拉取镜像。
4. 对 bind mount、env_file、configs、secrets 和相对文件依赖逐项解析。纳入产物或映射为登记资源；未解析、越界或依赖隐式远端环境的配置必须阻塞。
5. 明确宿主机端口、共享目录和服务范围；默认拒绝 privileged、宿主机根目录和 Docker socket 挂载等模板外能力。
6. 将生成配置、非敏感环境配置及镜像归档纳入同一个不可变 bundle。审批覆盖最终有效配置，上传后验证一致性。

运行时 secret 通过凭据引用在目标上以受限权限物化，记录引用版本，不进入普通 bundle、日志或审计明文。若第一期尚未实现该路径，则阻止需要 secret 的发布，不能自动降级为写入普通 Compose。

构建参数和运行环境分开配置。只有镜像加载路径时使用“唯一版本标签 + image ID 校验”，不能假定已推送仓库或存在 registry digest。

## 7. 状态、错误、取消与恢复

界面同时呈现三个独立维度：接入准备度、最近发布结果、当前服务观测结果。服务状态标注检查时间；缺少新证据时显示“未检查”或“状态待确认”，不得长期显示无依据的在线状态。

| 情况 | 顶层反馈 | 下一步 |
| --- | --- | --- |
| 构建或审批前检查失败 | 准备失败，线上服务未变更 | 定位配置或构建错误，重新准备 |
| 上传失败且确认未激活 | 发布失败，旧版本仍运行 | 重新准备，可复用校验通过的产物 |
| 更新失败且恢复、复验成功 | 发布失败，已恢复到上一版本 | 查看失败原因和恢复证据 |
| 恢复失败 | 发布失败，恢复失败 | 检查当前服务，显示具体人工恢复步骤 |
| SSH 断开或应用崩溃，无法确认副作用 | 状态待确认 | 只读核对远端证据后决定继续或恢复 |
| 首次部署失败，无受管上一版本 | 首次发布失败，无可自动恢复版本 | 检查现场或执行已登记接管恢复方案 |

“取消”表达取消请求，不表示瞬间结束。副作用开始后先核对状态，在安全边界停止或恢复；未知状态不能直接重试。应用重启后恢复运行展示并检查证据，不自动重复服务更新。

运行结果与恢复结果独立持久化；“恢复成功”不能将本次失败发布标为成功。需要扩展投影字段，不通过拼接前端提示推断业务事实。

人工回退创建新的运行，选择完整的历史镜像和配置，重新预检和审批，不重建历史源码、不修改原运行。回退默认不还原共享数据；数据结构不兼容时禁止自动恢复并说明原因。

版本清理保护当前版本、上一版本、运行租约、人工保留版本和未知状态相关产物。共享数据及备份不随发布版本清理；清理失败不改变已验证的发布结果。

## 8. 健康检查与代理

- 检查必须指定执行位置：服务器本机服务检查，或桌面端外部入口检查；两者结果分别展示。
- 服务器本机检查可访问回环地址，避免为检查开放应用端口。
- 配置协议、地址、端口、路径、预期状态码、超时、间隔、最大等待时间和必要性。
- JSON 接口可配置有限的结构断言，使用标准 JSON 解析；正文和日志有大小限制及脱敏。
- 不将任意重定向等同于健康；限定跳转目标，避免 basePath 或尾斜杠循环被掩盖。
- TLS 默认验证证书。私有 CA 使用明确的信任配置，不用全局忽略证书错误解决健康检查失败。
- 代理配置保持稳定时不在每次发布重载 Nginx。代理变更是单独可审核操作，先检查语法，再重载并验证，保留原配置恢复能力。
- 第一期没有持续后台监控承诺；显示最近观测时间，提供手动刷新及发布后的自动检查。

项目新增 Dockerfile、.dockerignore、compose.yml，并配置 standalone 构建；镜像包含运行代码、public 和静态资源，排除本地弹幕数据。容器工作目录固定 /app，明确 data 的写入权限。

目标根目录下 releases 存放不可变发布文件，shared/data 存放弹幕，.shellspan 存放受管状态；具体路径沿用执行器约定。Compose 场景的当前版本由服务实际镜像与发布记录共同核对，不将静态站点的 current 软链接当作容器切换手段。

首次接入必须先识别服务器已有运行方式。如已有 for-you 服务，备份原 data/danmaku.json 和启动、代理配置；先备份，再暂停旧服务写入，最终同步数据并校验，然后启动新容器。失败时按旧服务的明确启动方式恢复，不能以“第一次部署没有上一版本”忽略接管恢复。

当前接口在数据缺失时会返回预设弹幕，因此仅 GET 200 不证明数据迁移或写入权限正确。预检应检查文件、权限和迁移摘要；真实验收在隔离环境通过真实接口新增、读取、重启、升级、回退，确认同一条数据仍存在，不向生产注入虚假弹幕。

既有 Nginx 文件包含自签名证书配置，这不证明服务器已应用。外部 HTTPS 检查需先核实证书信任与入口；不自动关闭验证。单实例 Compose 更新可能短暂中断，首期明确展示此行为。

## 10. 数据模型与接口改造

| 对象 | 职责与关键字段 |
| --- | --- |
| Application | 名称、sourceBindingId、归档状态 |
| SourceBinding | 规范化本地路径、仓库身份、修订；仅本机保存 |
| Environment | applicationId、名称、SSH profile 引用、根目录、访问和数据配置、修订 |
| Workflow | environmentId、定义修订、模板来源；依然是执行语义唯一来源 |
| ReadinessReport | 配置修订、检查时间、逐项证据、阻塞项；不等同于审批 |
| Run | 现有不可变计划，补充 application/environment/source 修订绑定及恢复结果投影 |
| Release | 完整 bundle、目标环境、来源运行、数据兼容声明、保留状态 |

应用和环境表单写入时，通过后端事务更新关联工作流的受管字段和修订。准备操作解析、校验并冻结有效定义，不在运行时再次读取可变环境配置。运行继续使用现有 coordinator、CAS、approval 和 ledger。

高级编辑以稳定的节点角色映射识别模板字段。可识别字段允许表单编辑；自定义图无法映射时，相关字段只读并指向对应节点，不自动重建图或丢弃用户节点。模板升级必须预览差异，不静默覆盖自定义。

新增高层接口覆盖项目检测、应用/环境保存、接入检查、初始化计划准备和执行；现有 prepare 扩展绑定身份。所有接口经类型化 IPC，Rust 负责路径、权限、版本竞争和最终校验，不开放 effectful 单节点旁路。

既有工作流以“未关联应用”分组保持可访问，由用户显式绑定项目和环境。绑定生成新修订，不改历史记录；未绑定来源的工作流允许查看、取消和恢复已有运行，但阻止新发布。不要自动猜测源码目录，也不读取早期已废弃部署表。

## 11. 界面与交互验收要求

- 沿用无 Card 连续分栏、WorkbenchPageHeader 和现有 primitive；仅改部署中心范围。
- 宽容器显示应用列表与详情；窄容器用列表 Drawer，表单保持单列，避免页面横向滚动。
- 环境切换显示可读名称；发布按钮旁明确显示所选环境和主机，防止发错环境。
- 空态分别处理“无应用”“配置未完成”“尚未发布”“筛选无记录”；每种提供明确下一步。
- 一次性保存/刷新结果用 Toast；接入阻塞、待审批、恢复和未知状态用上下文状态区，避免重复通知。
- 长引导和审批使用固定头尾、正文滚动；键盘能完成所有步骤，关闭后焦点返回触发器。
- 所有文案中英同步。主界面显示业务名称，内部枚举和摘要放技术详情。
- 不因设计文档批准就顺手修改其他 UI；实施按下列阶段控制范围。

## 12. 串行实施计划与完成门槛

| 阶段 | 交付范围 | 退出条件 |
| --- | --- | --- |
| 1. 真实产物链路 | source binding、隔离快照、Compose 镜像绑定、文件依赖解析、协议更新 | 两个真实本地项目可独立构建；修改工作区不改变冻结产物；加载的镜像与配置一致 |
| 2. 应用与环境接入 | 数据模型、四步引导、检查报告、旧工作流显式关联 | 从空态接入 for-you；缺少条件能定位修复；不发生未经确认的远端写入 |
| 3. 发布体验 | 概览、准备详情、审批摘要、运行结果、服务观测投影 | 不进画布完成发布；过期、配置冲突和端口冲突能阻止执行 |
| 4. 首次接管与恢复 | 数据清单、恢复结果、历史版本回退、重启核对、保留策略 | 接管、升级、失败恢复及人工回退有真实证据；数据保持完整 |
| 5. 发布验收 | 双语、键盘、响应式、错误态、文档与端到端证据 | 全部必要测试和实际渲染检查通过，已知限制有明确呈现 |

不以模板可编译或画布连通作为部署成功证据。先用隔离 Linux/SSH 环境运行真实 Docker、Compose 和 SFTP，再在明确发布授权下验收目标主机，不通过 mock 或伪造响应代替执行。

最少验收矩阵：

1. 首次部署：页面、资源、弹幕读取正常，当前版本身份准确。
2. 连续升级：代码更新生效，已有弹幕保留，旧版本仍可定位。
3. 健康检查失败：使用真实故障版本或隔离网络故障；恢复旧服务并复验，发布结果仍为失败。
4. 人工回退：直接使用旧 bundle，保留新产生的共享数据。
5. 断网和应用重启：对上传、更新、验证边界分别中断；核对后不重复不可确定的副作用。
6. 审批漂移：切换主机、修改配置、改变现行版本后拒绝旧计划；仅移动节点不使其失效。
7. 资源竞争：相同 Compose 项目、端口或重叠根目录的不同环境不能并发更新。
8. 接入失败：目录缺失、权限不足、架构不匹配、磁盘不足、证书不可信均显示具体问题。
9. 数据完整性：真实文件读写、重启、升级和回退后保持一致；权限不正确不能被预设数据掩盖。
10. UI：约 1418、858、428 和 AI 面板挤压后的 778 px 容器下实际渲染；滚动、固定操作区、可读 label、焦点与键盘通过。

按影响运行就近前端和 Rust 测试，跨端修改执行 pnpm build、相关 Rust 集成测试及项目要求的检查。最终验收报告记录提交/工作区快照、工具版本、目标架构、运行 ID、版本身份、失败与恢复证据和未验证事项。

## 13. 完整性的判定

第一期只有在用户能够明确选择项目和环境、看懂首次接入缺口、通过同一产物完成部署、区分发布结果与服务状态、保护数据并恢复历史版本时才算闭环。

它仍可以有明确范围限制：仅单机、需要预装 Docker、未知服务接管需要人工步骤、更新可能短暂中断。限制必须在相关操作发生前显示，不能留到发布失败后才让用户发现。
