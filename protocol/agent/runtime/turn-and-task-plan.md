# Agent turn and task-plan contract

Status: implemented runtime contract.

## Current task and historical instructions

Every newly assembled request derives its current task from committed user input in the latest turn containing such input. Steering messages in that turn remain ordered with the original request. A recovery turn without fresh user task input retains the preceding task. Child Sessions also accept delegated input identified by their recorded parent; sibling reports, runtime messages, skill/plugin output and summaries cannot define a new task.

Session creation `goal` and `successCriteria` describe the initial task. Creation criteria are not injected as standing instructions for subsequent user turns, nor are inherited parent criteria treated as a child's delegated task criteria. Earlier one-time response instructions remain historical; applicable preferences and explicit continuations can still use the conversation and retained evidence. This scope follows committed input provenance and turn identities, without guessing task boundaries from keywords.

The native-tool request projection preserves its complete frozen `goal` and
explicit success criteria. If criteria are omitted, a goal of at most 2,048 UTF-8
bytes is also the default criterion. A longer goal remains intact in `goal`,
while the default criterion refers to completing that preserved goal; it is not
duplicated into the criterion field's smaller 2,048-byte limit. This projection
does not change tool arguments, target identity, permission mode or approval.

The current task snapshot is independently included as an append-only `shellspan.agent-instructions.v1` context injection before budget estimation and request freezing. Earlier `Current task request` snapshots remain in place in model history and are superseded by the latest injection so multi-turn conversations and steering preserve the provider's prompt-cache prefix (superseded legacy `ShellSpan Session instructions.` receipts from older logs are still omitted); original human messages and all audit events remain intact. Transport retries reuse their frozen input. Restart and compaction rebuild the snapshot from the durable log, rather than trusting a previous summary's claim about the current request.

The snapshot's JSON metadata identifies the turn, creation criteria when applicable, and each ordered request's original UTF-8 byte length. Committed request bodies are rendered verbatim in separate fences chosen so embedded fences cannot close the surrounding frame. Framing separators are outside the recorded body. This avoids adding a JSON display-escaping layer to user-supplied paths, source text, or JSON argument examples. It does not decode or repair model arguments: new tool calls still use the ordinary single argument JSON parse, frozen targets, and normal approval.

## Turn limits

Primary Agent turns have no default step limit. Cancellation, session turn limits, configured session token budgets, active-time budgets, model-stream deadlines, request retry policy, and the no-progress detector remain enforced independently. An explicitly configured step limit still acts as a recoverable boundary: reaching it records `stepBudgetReached`, closes the open step and turn, and returns the Session to idle without a terminal failure. The conversation renders the reason explicitly and offers a continuation action; queued user input may also start a fresh turn against the same durable Session.

Continuable subagents default to 50 model steps per turn when `budget.maxStepsPerTurn` is omitted (including when supplying other budget fields, and for legacy saved sessions whose persisted budget omitted it). The optional `budget.maxStepsPerTurn` lets the parent explicitly override that default with a limit of 1–64 model steps. Saved numeric limits remain enforced across reload and continuation. Reaching the per-turn step limit acts as a recoverable turn boundary: it records `stepBudgetReached`, preserves the Session and returns it to idle. The orchestration result explicitly marks `partial: true`, includes the stop reason and latest plan, and reports whether cumulative turn, tool, token and time budgets permit `send_child_input` against the same Session. The orchestration tool completing does not mean the child task completed. Continuation does not reset cumulative budgets, and exhausted children reject further input before being woken. The parent decides whether saved progress warrants continuation; it must not spawn replacements to bypass budgets.

Child snapshots expose `childContinuation` with `budgetExhausted` and `expiresAtUnixMs`, derived from the same cumulative admission calculation. The frontend refreshes this projection on child turn boundaries and events affecting an explicit token/tool budget, and checks the original wall-clock deadline even while idle, including on foreground resume. Exhaustion disables follow-up input with a localized handoff explanation while preserving the draft and in-flight stop, question and approval controls. An exhausted-budget rejection is permanent for that child and offers no failed-draft retry. Durable receipts still acknowledge already committed input. Older snapshots without this projection retain the deadline derived from their original creation time and `budget.timeoutMs`.

Each child model request with an effective step limit appends an ephemeral trailing user-role runtime reminder with its current per-turn step count and asks for verification and a partial-work handoff near the limit, keeping `system_prompt` and tool schemas static across steps for prompt-cache stability. One-shot and Fleet children retain their default limit of 16 model steps when the field is omitted; an explicit valid limit overrides that default. When a child reaches its final per-turn step (`step_index == limit` with `limit >= 2`), the runtime sets `tool_choice` to `none` (preserving `tools` on Anthropic, Chat Completions, and Responses; omitting `tools` on Ollama), asks for an evidence-based wrap-up synthesis, and skips the extra `completionCheck` step so the final summary is preserved cleanly. If a non-compliant provider still returns tool calls on that final step, one-shot children retain their hard single-turn contract (`stepLimitExceeded`) and continuable children pause with `stepBudgetReached`; their settlements also include partial-progress metadata. Use continuable children for implementation, debugging, and other multi-stage tasks. No-progress detection, cancellation, stream deadlines, cumulative turn/time limits and explicitly configured token/tool budgets remain independent of the per-turn step limit.

Child requests also include cumulative provider-reported total tokens, admitted tool calls, turns and elapsed time in the same ephemeral trailing reminder (without mutating `system_prompt`). Child token usage and tool calls are unlimited by default, including all Fleet roles. The optional `budget.maxTokens` enables a cumulative token limit only when explicitly supplied; omit it unless a token budget is requested. The optional `budget.maxToolCalls` enables a cumulative tool-call limit (1–4096) only when explicitly supplied by the parent. Omitting either field, including when omitting the entire budget, leaves that counter unlimited. `fleet_plan` accepts the same optional `budget`, persists it with the Fleet plan, and applies it separately to each child; no Fleet role adds an implicit tool-call limit. Existing saved numeric budgets remain enforced across reload and continuation. At 80% of an explicitly supplied token or tool-call limit, or the elapsed-time limit, the request advises immediate evidence-based handoff rather than further exploration. Unlimited counters do not trigger budget warnings, failures or continuation rejection. This is model guidance, not a guarantee of a final report or a reservation of additional tokens or tool calls. Missing provider usage remains unknown; total tokens include repeated inputs and are distinct from the model context-window limit. Manual cancellation, per-request model-stream deadlines, no-progress detection and the other child budgets remain unchanged.

Child and Fleet delegation resolve target IDs against the parent's bound target
and any frozen targets in its own delegation scope. The store checks the full
target metadata again when it commits the child, including project directories
and the SSH sandbox requirement.

Each Fleet has one active scheduler. A role's child identity is committed before
the child starts. Aborting a Fleet prevents further dispatch and cancels its
registered active children. If a scheduler stops before recording a target's
outcome, the target requires reconciliation before the Fleet can resume.
An aborted Fleet also prevents approval recovery for its children after restart,
even if their cancellation records were still being written when the app exited.

A Fleet Verifier records a completed `verify-target` step through `update_plan`
only after checking the assigned target. The runtime requires a completed native
read-only result on that target in an earlier model step of the same turn. It
records the child Session and result sequence as evidence. A normal child
completion alone leaves the target failed and counts toward the failure
threshold.

At that threshold, a text-only child response is deterministically settled as `incomplete` unless the current turn has a nonempty task plan whose steps are all completed. An absent plan does not imply successful completion. This handoff suppresses the normal extra plan-completion attempt, retains the report, and follows the existing incomplete one-shot/continuable settlement contract.

Failed child settlements, including token/tool/time/turn limits and provider errors, return `partial: true`, the latest `stopReason`, configured `budget`, cumulative `usage`, latest plan details and evidence references, and up to eight saved tool-result summaries (1,024 characters each, without raw tool data). `hasPartialResults` separately indicates whether an assistant report or completed tool result exists; `partial` alone does not claim useful work was completed. These fields are built from durable events without another model request. Successful later turns clear prior stop reasons. Cancellation returns preservation instructions and must not trigger an automatic restart.

The parent inspects the handoff and other child outcomes, continues only eligible children, or takes over missing work within its existing permissions and remaining task budget. It must not replay completed side effects or create replacement children to reset exhausted budgets. Its final response distinguishes verified results from specific gaps; collection failure is not evidence of an unhealthy target.

## Child failure recovery

A failed continuable child can recover in its original Session with `retry_child_agent({ childSessionId, turnId, content? })`. Inspect `failureRecovery` in the child handoff, or `snapshot.childFailureRecovery` from `inspect_child_agent`, before requesting recovery. The existing model-error retry action also supports eligible child transcripts through the typed `agent_runtime_retry_model` command. Transient model failures allow direct retry; request or configuration failures require fixing the cause and supplying bounded recovery instructions. Automatic per-request retries still run before this explicit recovery path.

Recovery requires the latest settled failed model turn, an available parent, fully settled tool calls, no uncertain native effects, and remaining cumulative budgets. Cancelled, completed, archived, one-shot and budget-exhausted children cannot recover through this path. One-shot children retain their single-turn contract. Parent permissions, child model selection, inheritance boundary, target, Session/task identity, plan, evidence and tool results remain unchanged. A recovery starts a new turn and consumes the original cumulative turn/token/tool/time budgets; it never uses root `session/resumed` or resets task counters.

`subagent/recovery_started` stores the failed turn ID, deterministic recovery ID and runtime recovery input in one committed event. It both reopens the child and enqueues that input, avoiding a reopen-without-input crash window. A lost reply or repeated request for the same failed turn reuses this receipt, including after the input was claimed; changed recovery instructions cannot replace an admitted attempt. On restart, unclaimed child inputs are paused and require explicit resumption. A cold recovery restores the owner chain and configured credentials before scheduling work; it does not wake an ended parent or change the saved child scope.

Only unfinished work is requested. Successful tool results stay in the Model Surface, and pending/uncertain calls block recovery rather than being replayed. During a recovery turn the native admission path rejects a write with the same native tool, target and structured execution arguments as an operation completed before recovery (ignoring the human-facing `explanation` field). Fresh reads remain available to verify state. This is exact structured-operation protection, not semantic equivalence detection for differently expressed shell commands; native confirmation, cancellation and audit rules still apply.

The child wait deadline uses the remaining cumulative elapsed-time allowance. On timeout, the runtime cancels and drains the child, then uses the same handoff path with `timedOut: true`, a `subagentTimeout` stop reason and a `TimedOut` tool result. The child snapshot retains its actual cancellation state; the timeout metadata distinguishes this shutdown from user cancellation and permits parent takeover. Explicit cancellation takes precedence and retains the instruction not to restart work. The parent tool result durably stores the timeout reason and saved progress.

## File editing and recovery

`apply_patch` accepts exactly one digest-bound UTF-8 file and standard unified diff (`---` / `+++` headers and counted `@@` hunks). It does not accept SEARCH/REPLACE or `*** Begin Patch` syntax. The model-facing schema and description reflect this native restriction. The runtime compares the resulting bytes with the original bytes before checkpointing or writing: a header-only, context-only, or otherwise unchanged patch fails, including during dry runs. `applied: true` is returned only after a changed file has been written and re-read successfully. `dryRun` never writes. A digest or context mismatch instructs the model to read the current file and rebuild the patch; it must not guess digests or discard unrelated content to fit a whole-file write.

`edit_file` replaces one unique exact `oldString` with `newString` in an existing UTF-8 file, bound to `precondition.sha256`. Each string is limited to 32 KiB of UTF-8; the old string must be nonempty, while an empty new string deletes the matched text. Missing, overlapping or multiple matches, unchanged text, and stale digests fail without writing. Native code generates a diff with diffy and reuses the patch preview, checkpoint, atomic write, cancellation and read-back verification pipeline. The result uses the patch result shape, including `files[0].afterSha256`. Existing 64 MiB file and 240 KiB exact-diff limits apply. There is no regex, fuzzy matching or replace-all behavior.

Within a turn, the no-progress detector checks cycles of one through five completed tool steps. Five complete repetitions trigger detection by default. Signatures include tool names, arguments, targets, statuses and normalized results, excluding volatile execution metadata. Different edit arguments or new results therefore allow productive recovery; three failures against one file are no longer a stopping condition.

Following Gemini CLI's tool-cycle recovery approach, the first detection appends a durable runtime `loop-recovery` message asking the model to inspect errors and change approach, and clears the repetition window. A second detection in the same turn ends the run with `noProgress`. Restart replays both the recovery marker and subsequent repetitions; session resume alone does not grant another recovery. New user input or a new turn renews the recovery opportunity. Pending user steering takes priority, and a queued follow-up can close the stalled turn immediately. Token, time, cancellation and step budgets still apply; recovery never guarantees another model request. Existing tool evidence and modifications remain available.

This adapts the tool-cycle threshold and single recovery opportunity from [Gemini CLI loop detection](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/services/loopDetectionService.ts) and [client recovery](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/core/client.ts). ShellSpan compares complete tool-step outcomes, not just call arguments. It does not implement Gemini's generated-text or model-assisted loop detection.

## Cumulative task token budget

The driver has no cumulative token admission limit by default (`max_model_tokens_per_session = 0`). Recorded input estimates and output usage continue to accumulate and rebuild from committed events after restart; crossing 2,000,000 tokens does not trigger a progress checkpoint or stop a request. Automatic context compaction, per-request context limits, no-progress detection, active-time and step limits remain independent and unchanged. Explicit child-agent budgets remain enforced.

An internal positive `max_model_tokens_per_session` enables the optional cumulative admission budget described below. Before each model request, the driver adds the estimated next input and output reserve to the current task's recorded input estimates and output usage. Context compaction does not reset this counter.

When that projection first reaches 90% of the task budget, the runtime saves a `task-budget-progress` artifact extracted from committed events. This contains the latest user constraints, completed work, unfinished plan steps, evidence references and suggested next steps. It makes no model call, does not replace history, and does not consume a tool approval. The attempt is tracked by committed events, so reopening the runtime does not repeat it on every step. A failed early save is recorded as `taskBudgetCheckpointUnavailable`; existing durable history remains available.

At the hard admission boundary, the next model request is not sent. The runtime refreshes the progress as a `task-budget-checkpoint` artifact and appends its bounded summary as runtime context before ending the turn and session with `taskTokenBudgetExceeded`. No model call is required even if the budget is already exhausted. Cancellation remains effective; an unavailable checkpoint store retains the original budget failure with `checkpointUnavailable` and never claims a checkpoint was saved. Existing events, effects and recovery gates remain intact.

The UI shows a text-only budget notice without a continuation button. Users continue by sending a message through the regular composer and normal resume path: `session/resumed` resets task counters and the early-checkpoint flag while retaining history and the final checkpoint in model input. Existing archive, child-session and target-availability restrictions remain in effect. No automatic reset or continuation occurs; original usage and progress remain in the audit log. The UI reports a saved continuation summary only when its artifact is present in the failed turn.

## Model output limit

When a model response ends with `length` or the provider returns `OUTPUT_LIMIT`, the runtime records available partial text and reasoning as an interrupted assistant message and discards any unfinished tool calls without executing them. Completed responses also record usage; provider errors retain their request failure evidence. The runtime adds a continuation instruction and starts another step in the same turn. At most two automatic continuation steps are allowed per turn. A third output-limit stop preserves available partial content and fails the Session with `outputLimit`; the UI shows a concise error and does not offer a separate continuation button. Cancellation and the existing turn and task budgets still apply to each step.

File-edit requests use a conservative advisory target of `min(8192, max(1, max_output_tokens / 2))` UTF-8 bytes. The target halves after each output-limit continuation (floor 1) and remains reduced for the rest of that turn. It never changes tool schemas or native argument limits. Necessary indivisible edits may exceed the suggestion within native safety bounds; unique substring replacement handles localized edits inside long lines without reproducing entire lines. This target is a generation heuristic, not an exact token conversion. Request preparation applies guidance before estimating context usage and freezing the provider request, so transport retries retain the same request contract.

Recovery instructions are generated from the request's available tools. Native file sessions inspect the destination and prefer exact replacements or focused patches; terminal-only sessions inspect and edit through their existing bounded command tool without being instructed to call unavailable file tools. Sessions with no applicable tools give a concise partial answer without claiming execution. Subsequent edits preserve unrelated content; build/test verification is required before claiming completion. Incomplete tool arguments are never stitched together or executed. This strategy guides the model and cannot guarantee compliance or completion. The UI projects `outputLimitContinuation` as a localized recovery notice without counting it as a process error; exhausted recovery remains an error. Persisted request-failure evidence is unchanged.

## Native, facade, and synthetic tools

The runtime separates model-callable tool names into three distinct layers:

1. **Native OS-effect tools** (`protocol/agent/runtime/built-in-tools.json`, `protocol/agent/runtime/tool-contract.schema.json`): the 24 built-in tools registered in `native/registry.rs` and executed inside `NativeToolEngine` only after single-use capability authorization and target revalidation.
2. **Model-facing native facades** (`modelFacades` in `protocol/agent/runtime/synthetic-tools.json`): model-facing aliases translated by `native_adapter.rs` before native admission — `run_terminal_command` routes to `exec_command` (`direct`) or `terminal_execute` (`boundTerminal`), `write_process_input` routes to `write_stdin`, and `call_mcp_tool` resolves dynamic workspace MCP server/tool capabilities.
3. **Synthetic Session-Runtime tools** (`syntheticTools` in `protocol/agent/runtime/synthetic-tools.json`): the 17 control-plane tools intercepted directly by the Session turn coordinator (`tool_pipeline.rs`) without entering `NativeToolEngine` or appearing in `built-in-tools.json` — `update_plan`, `read_tool_result`, `skill`, `ask_user_question`, `request_user_action`, and the 12 subagent/Fleet orchestration tools (`spawn_*`, `send_child_input`, `retry_child_agent`, `inspect_child_agent`, `cancel_child_agent`, `fleet_*`). Synthetic tools mutate durable Session state, read stored artifacts, load Skills into prompt context, pause the turn for user input, or orchestrate child Sessions within the caller's capability scope.

## Task-plan writes

Plan submissions do not reset the no-progress detector, even when their text or status changes. Successful `update_plan` signatures ignore the plan body, version and explanation. New user input, answered questions, explicit approvals, or new evidence can reset repetition tracking; duplicate evidence with the same kind and summary cannot. Reads participate in cycle detection; an unchanged read does not itself count as progress. The detector consumes committed events incrementally, computes each step signature once, and retains five signature digests with counters for periods one through five. Driver checks read these counters without replaying historical tool results. Restart rebuilds the same projection from the log; rejected batches do not alter it.

`update_plan` is a whole-list replacement for the current turn's task plan:

- `steps` is required and replaces the preceding list.
- Every step requires `id` and `status`. A new step also requires `title`. If `title` is absent for an ID in the current committed plan, the runtime preserves that step's title by ID, independent of list order. Explicit titles still undergo normal validation; empty, null or invalid values are rejected. No other fields are inherited, and steps absent from the replacement list are removed. Cleared plans and completed plans retired at the next turn cannot supply titles. The recorded tool call retains the original arguments; the committed `task/plan` contains complete validated steps. Rejection leaves the previous plan and version unchanged.
- `planVersion` is optional for model callers. The runtime assigns the next monotonic version; if the caller supplies `planVersion`, it acts as a concurrency guard and must equal that next version.
- Models should keep an `inProgress` step while work remains and update completed, blocked, or failed steps as soon as their state changes.
- A successful tool result reports the assigned version and counts for every plan status.

A final response triggers one completion check only when the current turn's latest plan still contains `pending` or `inProgress` work. If the remaining steps are `blocked` or `failed`, the runtime ends the turn as `incomplete` and releases the terminal turn guard without forcing another attempt. Such steps remain visible and are never reported as completed.

Ephemeral input placeholders in model history describe omitted content, not executable input. Model requests explicitly explain that historical input was omitted and new input is not replaced. Native tool preparation rejects these markers in terminal input, process input, terminal match text, and commands (including the native command name) before authorization or dispatch. The model must inspect current state and supply actual input or explain why it cannot proceed.

The latest plan remains visible after `turn/end`. The UI derives an `inProgress` row as paused unless its Session is running or waiting and the latest plan event belongs to the currently open turn. A subsequent `turn/start` retains the latest plan if any step is not completed, including after terminal disconnection, reconnection and explicit Session resume. Retained rows stay paused until that turn records its own `task/plan`; a new user request or a running Session alone does not reactivate earlier work. Activation follows committed turn identifiers, never inferred user wording. Missing ownership (including a snapshot without event replay) is treated as paused. This preserves completed rows, unfinished rows, details, evidence references and the plan version until a new `update_plan` replaces the whole list (an empty list explicitly clears it). A plan whose steps are all completed is cleared when the next turn starts. Retention is a projection rule: it does not replay tools, grant execution permission, or change the current-turn completion check. Durable `task/plan` events remain in Activity history for audit and replay.

Each newly assembled model request includes a static task-plan policy in its system prompt and delivers the latest committed nonempty plan as JSON in an append-only runtime context injection (`shellspan.task-plan.v1`), before token-budget estimation and request freezing. Because the system prompt stays invariant across plan updates and `ensure_model_context` appends a new snapshot only when the plan or its ownership changes, updating the plan preserves the provider's prompt-cache prefix. Earlier snapshots remain in history and are superseded by the latest snapshot; after history compaction removes prior injections, the next step automatically appends the latest snapshot again. This snapshot does not itself change plan ownership. For a retained plan, the model is instructed to adopt the complete list through `update_plan` before using further task tools when the latest user request continues that work; unrelated questions leave it paused. Current-turn guidance requires immediate evidence-based updates and a `blocked` status with details before asking for a user decision. This is model guidance, not automatic status inference or a guarantee of model compliance. Retry attempts retain the frozen request, child sessions inheriting history strip `shellspan.task-plan.v1` injections, and the existing current-turn-only completion check is unchanged.

When no nonempty plan exists, including after explicit clearing or retirement of a completed plan at the next turn, the same `shellspan.task-plan.v1` context injection explicitly reports that absence (superseding any earlier snapshot). A new submission must include `id`, `title` and `status` for every step; historical plans and compaction summaries cannot supply omitted titles. This notice does not recreate a plan or authorize repeating completed work.

## Runtime projections and stream persistence

The latest step's current model response can become the final answer. Tool-bearing commentary remains in the process disclosure with its tool activity. Interrupted attempts and output-limit prefixes stay visible as separate responses in both the Agent and Ask transcript. A retry starts a fresh response, and the turn footer copies only a completed answer. A normal stop with reasoning but no answer text or tool calls is handled as an empty response.

Normally completed turns with a committed final answer automatically fold their process details. Explicit reader choices are retained across model requests and view remounts; focus or selected text inside the process body prevents automatic folding on completion. Failed, cancelled, incomplete, waiting, partial-history and interleaved-input processes default to expanded without automatic folding. A completed turn without a committed final answer also defaults to expanded. Readers can manually collapse or expand the process in every status, including after failure. Folding changes presentation only; durable events, tool evidence and user input order are unchanged.

Session token usage, active duration, turn count and current-turn step count advance with committed events and rebuild from the durable log on startup. Snapshot projections are cached for an unchanged record; event commits and archive changes invalidate the cache. Driver queries borrow events under the store lock rather than cloning the full history; current-turn checks start at the recorded turn offset.

Assistant streaming deltas are buffered for periodic flushes at 40 ms. Each batch is bounded at 64 KiB or 128 events. A single background writer accepts at most two queued batches. Size-triggered, periodic and final flushes all use this writer. Synchronous model callbacks run on a blocking worker, so bounded queue pressure cannot block the async scheduler. The driver cancels and joins that worker before closing the sink, and a persistence fence drains accepted batches before response, retry, timeout or cancellation settlement. The preview holds unfinished credential boundaries across flushes and splits redacted text into UTF-8 events. Published events follow durable batch writes. Tool execution and approval boundaries are not buffered. A failed write ends the stream. If settlement cannot be saved, the committed-events page reports a separate storage fault at the last committed sequence. An abrupt process exit can lose the uncommitted tail, and native effects retain their existing recovery semantics.
