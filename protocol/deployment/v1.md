# ShellSpan Deployment Protocol v1

Status: Historical Phase 4 contract. Superseded for new plans by
[`v2.md`](./v2.md). Phase 4 persistence, approval-plan, read-only preflight, fixed local
Docker Buildx artifacts, deployment center, and approved artifact transfer into
isolated remote staging. This document defines the durable contract for the
single-host Docker Compose MVP. It does not authorize remote deployment
execution or activation.

## 1. Authority and trust boundary

The native Rust Deployment Runtime is the sole execution authority. The UI,
Agent runtime, quick actions, imported workflow data, remote hosts, and model
tool calls are untrusted request sources. They may propose a workflow or ask the
runtime to create a run, but they cannot execute a deployment step, manufacture
an approval, skip reconciliation, or mutate the event ledger.

Every effectful step must be selected from the fixed v1 action vocabulary,
validated at the Tauri boundary, bound to an immutable approval summary, and
executed by the Rust runtime. Agent and quick-action entry points follow the
same approval path as manual entry points. An approval is never inferred from
the source of a request.

Version 1 does not permit arbitrary local or remote shell steps. In particular,
a workflow cannot contain a command string, script, shell interpreter, Docker
argument tail, or Nginx directive. Future fixed-purpose operations require a
protocol revision and a reviewed native implementation; they must not be added
as generic command escape hatches.

Credentials, private keys, passwords, API keys, and tokens are outside this
protocol. Workflows identify an existing connection profile. The native
credential subsystem resolves credential references only at execution time.
Secrets must not appear in workflow JSON, approval summaries, events, logs, or
diagnostics.

## 2. Versioned workflow

A v1 workflow has `schemaVersion: 1` and only these typed inputs:

- a local source directory;
- a fixed `dockerBuildx` build plan containing a normalized relative context,
  normalized relative Dockerfile path, one supported Linux platform
  (`linux/amd64` or `linux/arm64`), an untagged lowercase image repository,
  and `zstd`, `gzip`, or `none` artifact compression;
- one existing connection profile and a normalized, non-root remote release
  directory;
- a Docker Compose project name, one or more relative Compose YAML paths, an
  optional service allowlist, and whether the fixed pull action is requested;
- an optional bounded HTTP health check described by path, expected status, and
  timeout; and
- a bounded release-retention count.

Unknown fields fail validation. Paths must be normalized and may not traverse
parents. Identifiers, list sizes, document sizes, retention, status codes, and
timeouts are bounded by the native domain validator. A saved workflow is
revisioned; a run freezes the workflow revision it was planned from.

The eventual MVP executor may implement only this fixed sequence:

1. validate and freeze the workflow revision;
2. produce a content-addressed release artifact and SHA-256 digest;
3. construct the approval summary;
4. obtain explicit approval for that exact summary;
5. stage the release through fixed-purpose transfer APIs;
6. invoke reviewed Docker Compose operations for the approved project, files,
   and service allowlist;
7. activate the release and perform the typed health check; and
8. record the terminal result and bounded cleanup summary.

Phase 2A implements the protocol, persistence, deterministic approval plans,
typed IPC, and validation. Phase 2B adds fixed read-only Git and SSH preflight
collection. Phase 3 adds a local-only, fixed Docker Buildx artifact builder.
Plan creation performs no upload, remote write, remote Docker mutation, Compose
mutation, or reverse-proxy operation.

## 3. Approval summary

Before an effectful action, the runtime persists and presents an approval
summary with `schemaVersion: 1`. It contains:

- workflow ID and revision;
- operation kind (`deploy`, `resume`, or `rollback`);
- the frozen source revision and dirty-state flag;
- the target profile ID, profile update revision, host, port, username,
  authentication method, and optional jump-host identity, but no credential
  references or credential values;
- the normalized remote root;
- Compose project, Compose files, and service allowlist;
- current, target, and rollback release identities, each including its
  lowercase SHA-256 artifact digest when present;
- a bounded, structured preflight result summary; and
- the ordered fixed actions, chosen from `stage_release`, `compose_pull`,
  `compose_up`, `verify_health`, `activate_release`, and `restore_release`.

The runtime canonicalizes unordered service and preflight-check collections,
serializes the closed summary deterministically, computes a SHA-256
`planDigest`, and derives `planId` as `plan-<planDigest>`. The summary includes
`generatedAt` and a bounded `expiresAt`; an expired plan is invalid. The run
stores the canonical summary and digest. Any unknown field, digest mismatch,
expiry, workflow revision change, target identity change, source revision
change, release selection change, preflight-summary change, Compose selection
change, operation-kind change, or action change fails closed. Once execution
starts, a changed plan requires a new run. Approval records contain no
credentials or raw logs and are limited to 64 KiB.

An Agent confirmation in conversation is not runtime approval. A quick action
is not runtime approval. Only the native approval mechanism may append
`approval_granted` and transition the matching run to `approved`.

## 4. Run state machine

Durable run states are:

- `planned`: a frozen plan exists but has not entered approval;
- `awaiting_approval`: the exact approval summary awaits a user decision;
- `approved`: the persisted summary digest is approved and execution may begin;
- `reconciling`: the runtime is comparing durable state with observable host
  state before deciding whether any action is safe;
- `in_progress`: at least one approved effectful action is active or completed;
- `verifying`: deployment effects completed and typed verification is running;
- `succeeded`: verification and durable recording completed;
- `cancel_requested`: cancellation was recorded and the runtime is stopping at
  a safe boundary;
- `canceled`: the runtime proved no approved action remains active;
- `failed`: the runtime has a definite bounded failure result; and
- `state_unknown`: a crash, disconnect, timeout, or ambiguous remote response
  prevents the runtime from proving the deployed state.

Allowed transitions are:

```text
planned -> awaiting_approval | canceled
awaiting_approval -> approved | canceled | failed
approved -> awaiting_approval | reconciling | in_progress | cancel_requested | failed
reconciling -> approved | in_progress | canceled | failed | state_unknown
in_progress -> verifying | cancel_requested | failed | state_unknown
verifying -> succeeded | cancel_requested | failed | state_unknown
cancel_requested -> canceled | failed | state_unknown
state_unknown -> reconciling
```

`succeeded`, `canceled`, and `failed` are terminal. A terminal run is never
reopened. Resume and rollback create new linked runs rather than mutating a
terminal run. The native state-transition validator rejects all transitions not
listed above.

## 5. Event ledger

Each run owns an append-only sequence beginning at 1. The next event must be
exactly `last_event_sequence + 1`; duplicates and gaps fail. Events are ordered
by `(run_id, sequence)`, not wall-clock time. Inserting an event atomically
advances the run's last sequence. Existing events are immutable.

The v1 event kinds are `run_created`, `approval_requested`, `approval_granted`,
`approval_rejected`, `reconciliation_started`, `reconciliation_completed`,
`status_changed`, `cancellation_requested`, `resume_linked`, `rollback_linked`,
`run_succeeded`, `run_canceled`, and `run_failed`.

An event stores a bounded human-readable summary (at most 4 KiB) and an optional
bounded structured payload (at most 64 KiB). Raw process output, artifact
content, environment dumps, and unbounded logs are not event payloads. A later
runtime may expose a separately bounded, redacted live-output channel, but the
durable ledger records only summaries and stable identifiers.

## 6. Cancellation, uncertainty, resume, and rollback

Cancellation is cooperative after approval. A request first appends
`cancellation_requested` and transitions to `cancel_requested`. The runtime
stops before the next safe fixed-purpose action and attempts to cancel the
current owned operation. A `planned` or `awaiting_approval` run may transition
directly to `canceled` because no effectful action has started. Any other run
may transition to `canceled` only after the runtime proves that no deployment
action remains active. Cancellation never claims to undo an already applied
Compose change.

If completion cannot be proved—for example after application exit, SSH loss,
timeout, or an ambiguous Docker response—the run becomes `state_unknown` and
sets `reconciliation_required`. No deploy, resume, rollback, cleanup, or retry
action may proceed from uncertain state. The runtime must first enter
`reconciling`, inspect only the fixed, approved release and Compose identities,
and append the reconciliation result.

A resume is a new run with `operation_kind: resume` and `source_run_id` pointing
to the prior run. It always reconciles before effects and requires a new
approval summary; prior approval is not reusable.

A rollback is a new run with `operation_kind: rollback` and `source_run_id`
pointing to the run being reversed. It targets a known retained release and uses
the fixed `restore_release` action. It requires a new approval, verifies the
restored service, and follows the same cancellation and uncertainty rules.
Rollback is not available when the target release identity cannot be proved.

## 7. Persistence and deletion

Schema v2 adds `deployment_workflows`, `deployment_runs`, and
`deployment_run_events`; schema v3 adds immutable-plan and state-transition
guards. Workflows reference existing connection profiles.
Runs reference workflows; events reference runs. Foreign keys are enabled.
Deleting a workflow cascades to its runs and events, while deleting a referenced
connection profile is restricted. Runs and events cannot be deleted directly.
The native repository rejects workflow deletion while any run exists; the SQL
cascade is an integrity rule for controlled whole-workflow cleanup rather than
a product bypass. Product code should normally archive or disable workflows;
a future retention policy may add explicit archival before exposing destructive
deletion in the UI.

JSON columns and event summaries are bounded and validated. The deployment
tables do not store credentials or raw logs. Database migrations execute
incrementally in transactions and append a named version record. Missing,
gapped, renamed, unknown, or higher migration histories fail closed.

## 8. Compatibility

Workflow and approval document versions are independent of the SQLite schema
version. Readers accept only versions they explicitly implement and reject
unknown fields in v1 documents. New optional behavior must use a new protocol
document version unless an older reader can safely ignore it without changing
approval or execution semantics.

Run statuses and event kinds are closed v1 enums. New values require coordinated
Rust, TypeScript, database migration, protocol, and test updates. A future
runtime may project old events into a newer read model, but it must preserve the
original event sequence and approval digest. Downgrade from an unknown or higher
database schema is unsupported and fails closed; automatic destructive rollback
of schema migrations is forbidden.

## 9. Phase 2A IPC and Phase 2B preflight

The Phase 2A Tauri boundary exposes workflow CRUD, pure-data plan creation and
plan lookup, run lookup/listing, and bounded event-window queries. Plan creation
atomically creates a `planned` run and sequence-1 `run_created` event. Runtime
state transitions use compare-and-swap over both the expected status and last
event sequence, and append the next contiguous event in the same transaction.

Phase 2B exposes `deployment_preflight` and
`deployment_cancel_preflight`. In Phase 3 the preflight request contains only
an operation ID, workflow identity and expected revision, an opaque runtime
artifact reference, and bounded plan/preflight timeouts. It contains no local
path, local argument, remote command, shell fragment, digest override, or
credential value. The native boundary resolves and verifies the reference,
then derives the target release ID and digest from its manifest.

The native preflight reverifies the artifact manifest and archive, freezes the
saved workflow and profile, resolves secrets
through credential references, and uses the existing known-host and reviewed
SSH boundaries. It returns `DeploymentPlanCreateInput` only when every blocking
check passes. That input includes the preflight-time non-secret target identity;
plan creation reloads the profile and rejects any mismatch before persisting a
run. The UI submits the returned value to the Phase 2A plan-creation boundary
and retains the returned `planId`, `planDigest`, `runId`, and `expiresAt`.
Preflight never writes deployment tables directly.

The local source collector runs only these fixed read-only Git queries in the
canonical `sourceDirectory`, which must equal the discovered Git project root:

- `git rev-parse --show-toplevel`;
- `git rev-parse --verify HEAD^{commit}`; and
- `git status --porcelain=v1 --untracked-files=normal --no-renames`.

Git output is drained through bounded collectors, time and cancellation are
checked while child processes run, and the revision must be a 40- or 64-byte
lowercase object digest. The collector never invokes a shell and never changes
the repository.

The remote collector invokes one compiled-in POSIX read-only probe. The only
runtime parameter is the validated remote root, passed as a strictly quoted
positional argument. The probe reads OS and architecture, root reachability,
available disk, and availability of Docker, Docker Compose, `flock`, a
SHA-256 tool, and a supported tar compression pair. It also reads release
metadata from the following closed layout:

```text
<remoteRoot>/current -> <remoteRoot>/releases/<releaseId>
<remoteRoot>/releases/<releaseId>/.shellspan-artifact-sha256
```

The digest file contains one lowercase SHA-256 hex digest. Release identifiers,
digests, counts, and all SSH output are bounded and validated before they enter
the preflight result. Malformed or duplicate metadata fails closed. A missing
current release is a warning for an initial deployment; an inaccessible root
or missing required tool is blocking. Workflow or profile drift before the
result is returned fails with a stable displayable category.

Cancellation is operation-scoped across local Git and SSH work. Timeouts,
cancellation, target drift, missing credentials, known-host rejection,
connection failure, command failure, parse failure, and output-limit failure
remain distinguishable on the wire. Neither a failed nor a blocked preflight
silently creates a plan.

Read-only preflight still performs no transfer, SSH mutation, Docker/Compose
mutation, activation, health-check execution, reconciliation, or rollback. The
deployment center exposes Phase 4 transfer only after a matching artifact,
preflight result, unexpired plan, and native approval exist; its Phase 5 remote
execution control remains unavailable.

## 10. Phase 3 local artifact build

Phase 3 exposes these native local-build interfaces:

- `DeploymentArtifactBuildRequest`: operation ID, workflow ID and expected
  revision, frozen source revision, fixed `dockerBuildx` builder kind, and a
  bounded timeout;
- `DeploymentArtifactBuildProgress`: operation ID, fixed step identifier,
  monotonic sequence, completed/total byte counts where known, and a fixed,
  redacted bounded summary;
- `DeploymentArtifactBuildResult`: workflow revision, release ID, lowercase
  artifact SHA-256, artifact size, opaque local artifact reference, frozen
  source revision, versioned manifest, reuse flag, and a closed
  success/cancel/timeout/failure category;
- `deployment_artifact_source_snapshot(workflowId, expectedRevision)` for the
  local UI to obtain the immediately revalidated Git request snapshot;
- `deployment_build_artifact(input)`; and
- `deployment_cancel_artifact_build(operationId)` for cooperative cancellation.

The request never contains a program, argument tail, environment map, shell
fragment, release tag, artifact destination, or compressor executable. The
native runtime invokes programs with `program + args` and never a shell. Its
closed sequence is:

1. reload and freeze the enabled workflow revision;
2. canonicalize the project root, build context, Dockerfile, and Compose files,
   and reject any path or symlink escape;
3. run the fixed Git root, HEAD, and dirty-state queries and require them to
   match the request snapshot; dirty working trees fail closed;
4. run `docker version`, `docker buildx version`, and the selected fixed
   compressor version query;
5. run `docker buildx build --load --progress plain --platform <platform>
   --file <canonicalDockerfile> --tag <repository>:<releaseId>
   <canonicalContext>`;
6. run the fixed image-ID inspect and `docker image save --output <ownedTemp>
   <repository>:<releaseId>` operations;
7. apply only the workflow-selected fixed `zstd`, `gzip`, or `none` transform;
8. copy the bounded Compose files into runtime-owned staging, hash every staged
   file, revalidate the workflow and Git snapshot, and atomically publish; and
9. reopen and verify the published manifest, archive, staged Compose files,
   permissions, sizes, and hashes before returning success.

Each child runs in an owned process group or Windows job. Cancellation,
timeout, or output/size overflow terminates the process tree. Standard output
and diagnostics are drained through hard limits and known secret values are
redacted; raw process output is not persisted or emitted as build progress.
The Docker child receives only a reviewed environment allowlist and never a
caller-provided environment.

Artifacts live below the Deployment Runtime `artifacts-v1` staging root.
Directories are private (`0700` on Unix) and files have no group/other access
(`0600` on Unix). A build uses a private temporary directory, fsyncs files and
directories, and renames the whole directory into its content-addressed final
name. Failure or cancellation drops the temporary directory. An existing final
directory is never overwritten: an identical request reuses it only after full
verification, while invalid or conflicting content fails closed.

The version-1 manifest contains:

- manifest schema version and content-identity SHA-256;
- workflow ID and revision;
- frozen source revision and dirty state;
- generated release ID and platform;
- image repository, generated tag, and inspected image ID;
- archive file name, compression, bytes, and SHA-256;
- each staged Compose path, runtime file name, bytes, and SHA-256;
- creation time; and
- `manifestDigestSha256`, computed over the compact canonical manifest with
  that digest field omitted.

The artifact reference is an opaque
`deployment-artifact-v1:<contentIdentity>:<manifestDigest>` token, never a
caller-selected filesystem path. Preflight resolves it only below the runtime
staging root and verifies the manifest, archive, Compose files, permissions,
workflow revision, and source revision before opening SSH. Its release ID and
archive digest become the approval plan's `targetRelease`.

Phase 3 is local-only. It does not perform SFTP or upload, open SSH for mutation,
write a remote file, run remote `docker load`, run remote Compose, change Nginx,
activate a release, or roll back.

## 11. Phase 4 ArtifactTransfer boundary

Phase 4 consumes the Phase 3 opaque reference and the exact approved plan. It
does not accept an arbitrary local path, remote file name, remote destination,
credential value, command, or shell fragment. Its closed surface is:

- `DeploymentArtifactTransferRequest`: operation ID, plan ID and plan digest,
  workflow ID and revision, artifact reference, frozen source revision and
  target identity, normalized remote root, release ID, release digest, and a
  bounded timeout;
- `DeploymentArtifactTransferProgress`: operation ID, monotonic sequence,
  fixed step (`revalidate`, `lock`, `stageArchive`, `stageCompose`,
  `verifyRemote`, or `complete`), one manifest-relative file identifier,
  completed/total bytes, and a fixed redacted bounded summary;
- `DeploymentArtifactTransferResult`: operation ID, plan ID, release ID,
  opaque verified remote staging identity, transferred bytes, verified remote
  digest, status, reuse/resume flags, and a closed failure category; and
- `deployment_cancel_artifact_transfer(operationId)`.

Before the first connection and again before returning success, the runtime
reloads the plan, workflow, profile, Git source, and local artifact. It requires
an unexpired `approved` run whose canonical digest, `stage_release` action,
workflow revision, source revision/dirty state, frozen non-secret target
identity, remote root, release ID, and release digest exactly match the request
and the verified manifest. A `planned` or `awaiting_approval` run cannot write
remote state. Profile or jump-host revision drift, host-key failure, missing
credential reference, manifest drift, archive drift, source drift, or expiry
fails closed. The runtime resolves credentials only after these checks and
reuses the normal credential reference, Known Hosts, jump-host, and reviewed
SSH/SFTP boundaries. The request and all progress/results remain secret-free.

The runtime canonicalizes the approved remote root through SFTP, rejects
control characters and path traversal, and refuses any existing symbolic-link
or non-directory staging component. It may create or write only below:

```text
<canonicalRemoteRoot>/.shellspan/staging/<artifactContentIdentity>/
```

The content identity comes from the verified manifest. Archive, manifest, and
Compose file names also come only from that manifest. Phase 4 never writes
`current`, `releases`, Compose runtime configuration, Nginx configuration, or
any caller-selected remote path.

Each content directory has an exclusive operation lock. Every staged file has
a deterministic `<final>.part` path shared across safe retries and a
deterministic final path. Before resuming, the runtime requires the partial to
be a regular file, requires its size not to exceed the local file, and streams
SHA-256 over both the remote and local prefixes. A matching prefix resumes at
the exact byte offset. A mismatching or oversized partial may be removed only
while the operation owns the content lock, after which transfer restarts from
zero. Cancellation and timeout remove the operation lock when that removal can
be proved, but preserve matching partials for a later invocation.

All file copying is bounded-buffer streaming and is independent of the Agent
artifact memory limit. Blocking Git, hashing, SSH, and SFTP work runs on a
blocking worker. Progress sequences never decrease, cancellation and deadline
checks occur between chunks, and connection loss may reconnect a bounded
number of times and resume only after frozen inputs are revalidated again.

After the final byte is written, the runtime streams the remote partial through
byte-count and SHA-256 verification, calls remote `fsync` and close, and uses an
exclusive atomic rename. An existing final file is reused only if its exact
size and SHA-256 match the verified local manifest; otherwise it is an immutable
conflict and is never overwritten. After rename, the final file is streamed
through the same verification again. Success is returned only after every
archive, `manifest.json`, and staged Compose file passes and the local artifact
and plan pass their completion-time revalidation.

The success identity is
`deployment-staging-v1:<contentIdentity>:<manifestDigest>`. It is opaque to the
UI and gives Phase 5 no authority to choose a path. Status is closed over
`succeeded`, `cancelled`, `timedOut`, `failed`, and `stateUnknown`. Failure
categories distinguish invalid request, missing/mismatched/expired/unapproved
plan, workflow/source/target/artifact/release drift, credential and host-key
failures, connection failure, unsafe path, final conflict, invalid partial,
remote I/O, digest mismatch, cancellation, timeout, uncertainty, and internal
failure. An ambiguous disconnect exhausts bounded reconnects as `stateUnknown`;
it never claims success or deletes a possibly active path.

## 12. Frozen Phase 5 RemoteRunner boundary

Phase 5 is not implemented by Phase 4. Its initial input is nevertheless frozen
so the staging result cannot later become a command or path escape hatch:

- `DeploymentRemoteRunnerRequest`: operation ID, exact plan ID/digest,
  workflow revision, Phase 3 artifact reference, successful Phase 4 transfer
  operation ID, frozen source and target identities, approved remote root,
  release ID/digest, the opaque staging identity, and a bounded timeout;
- `DeploymentRemoteRunnerProgress`: operation ID, monotonic sequence, closed
  step (`revalidate`, `lock`, `loadImage`, `prepareRelease`, `composePull`,
  `composeUp`, `verifyHealth`, `activateRelease`, or `recordResult`), closed run
  status, and a bounded redacted summary; and
- `DeploymentRemoteRunnerResult`: operation ID, plan/release identities,
  terminal status, observed active/rollback release identities,
  `reconciliationRequired`, and a closed failure category.

The Phase 5 failure categories are `invalidRequest`, `planNotFound`,
`planDigestMismatch`, `planExpired`, `planNotApproved`, `workflowChanged`,
`sourceChanged`, `targetChanged`, `releaseChanged`, `stagingInvalid`,
`lockConflict`, `imageLoadFailed`, `releasePrepareFailed`, `composePullFailed`,
`composeUpFailed`, `healthCheckFailed`, `activationFailed`, `cancelled`,
`timedOut`, `stateUnknown`, and `internal`.

RemoteRunner may start only from a `succeeded` ArtifactTransfer result that
still matches the current artifact reference, plan digest, workflow revision,
source revision, target identity, remote root, release identity, and opaque
staging identity. Any change immediately invalidates that result. The status
set is `running`, `verifying`, `succeeded`, `cancelRequested`, `cancelled`,
`failed`, and `stateUnknown`; unknown remote completion always requires
reconciliation. This frozen interface does not itself authorize `docker load`,
Compose, activation, Nginx, release deletion, cleanup, or rollback.
