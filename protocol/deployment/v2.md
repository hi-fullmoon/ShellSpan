# ShellSpan Deployment Protocol v2

Status: Phase 7 user experience, durable history, entry-point navigation, and
notification integration, building on
native approval, the fixed RemoteRunner, health verification, same-run
automatic restore, and optional Nginx reload. This document imports
the Phase 1–4 trust, artifact, transfer, persistence, and bounded-output rules
from `v1.md`; the rules below replace conflicting v1 text.

## 1. Compatibility and versions

New workflows use `schemaVersion: 2`. Readers continue to accept a v1 workflow
only as `reloadNginxAfterHealthy: false`; enabling that behavior in v1 fails
closed. New approval summaries use `schemaVersion: 2`, bind the exact opaque
`artifactReference`, and use the expanded fixed action vocabulary below. Stored
v1 summaries remain readable with their original canonical digest, but they
cannot authorize Phase 5 execution.

SQLite schema v4 adds immutable successful transfer receipts. A receipt binds
the transfer operation, run, plan ID/digest, workflow revision, artifact
reference, source and target identities, remote root, release ID/digest, and
opaque staging identity. A RemoteRunner cannot start without an exact receipt.

## 2. Workflow and approval summary

The only new workflow field is the strictly typed boolean
`reloadNginxAfterHealthy`, defaulting to `false`. It may be true only when a
typed HTTP health check exists. It never accepts an Nginx command, configuration
fragment, unit name, argument, or path.

The ordered v2 action vocabulary is closed over:

- `stage_release`, `prepare_release`, and `load_image`;
- `compose_config`, optional `compose_pull`, then `compose_up`, and optional
  `verify_health`;
- optional `validate_nginx`, `reload_nginx`, and `reverify_health`;
- `activate_release`;
- `automatic_restore` when an exact rollback release is frozen; and
- `restore_release` for a separately approved rollback operation.

The full non-secret summary includes the exact plan and run identities, run
event revision, expiry, workflow revision, artifact reference, source revision
and dirty state, target profile revision and non-secret SSH/jump-host identity,
remote root, Compose project/files/services, current/target/rollback release
IDs and SHA-256 digests, preflight checks, and all fixed actions. Credentials
and raw command output remain forbidden.

## 3. Native approval

Plan creation persists `planned`. A native approval request binds `planId`,
`planDigest`, `runId`, the exact `runRevision`, and `expiresAt`, then atomically
appends `approval_requested` while transitioning to `awaiting_approval`.

Approval accepts the same exact binding. Before committing it, the runtime:

1. reloads the immutable plan and workflow revision;
2. verifies the canonical summary digest and expiry;
3. reopens the opaque artifact and verifies manifest/archive/Compose hashes;
4. rereads the canonical Git revision and dirty state;
5. reloads the non-secret target profile identity;
6. reruns fixed read-only remote preflight and compares every check, release,
   target, and source identity; and
7. calls `verify_for_approval` on the canonical frozen inputs.

Only then may one transaction append `approval_granted` and transition to
`approved`. Rejection atomically appends `approval_rejected` and transitions to
`canceled`. Agent and quick-action surfaces have no approval command or implied
approval authority; they can only create work that a user later reviews in the
native approval UI.

## 4. Phase 5 RemoteRunner boundary

`DeploymentRemoteRunnerRequest` contains only an operation ID, exact plan
ID/digest, run ID/revision/expiry, workflow revision, Phase 3 artifact
reference, successful Phase 4 transfer operation ID, frozen source and target
identities, approved remote root, release ID/digest, opaque staging identity,
and timeout. Unknown fields fail. There is no command, executable, argument
tail, environment map, local path, remote destination, or credential.

Before remote launch and before accepting a terminal observation, the native
runtime revalidates the plan/run binding, workflow, Git source, target profile,
artifact, immutable transfer receipt, staging identity, and release digest.
Start requires the exact `approved` run revision. Completion requires the same
immutable approved plan while the run is `in_progress`, `verifying`, or
`cancel_requested`.

Progress steps are closed over `revalidate`, `lock`, `prepareRelease`,
`loadImage`, `composePull`, `composeConfig`, `composeUp`, `verifyHealth`,
`validateNginx`, `reloadNginx`, `reverifyHealth`, `activateRelease`,
`restoreRelease`, and `recordResult`. Progress summaries are fixed, bounded,
and secret-free. Terminal results are `succeeded`, `rolledBack`, `cancelled`,
`failed`, or `stateUnknown`.

## 5. Installed runner and remote ledger

The runner is a POSIX script compiled into the application. Its version and
SHA-256 are part of launch state. The runtime installs it under a
SHA-256-addressed filename, writes an immutable, digest-protected, strictly
ordered data request, verifies both, writes `launch.accepted`, and starts the
runner with detached standard streams via `nohup`. It does not depend on an
interactive password after launch.

The runner takes only the runtime request file and run directory. It validates
every key in exact order, rejects extra/missing/unknown fields, verifies its own
SHA-256 and request digest, and derives all paths below the approved remote
root. It obtains one non-blocking `flock` deployment lock per workflow root.

Remote state lives only below:

```text
<remoteRoot>/.shellspan/runs/<runId>/
```

Status is atomically replaced. Each event is atomically published under a
contiguous sequence and is immutable. Every effectful action writes an intent
before execution and an outcome after observation. The native runtime imports
those observations into the local immutable event ledger. Missing, gapped,
unknown, malformed, or ambiguous remote state yields `state_unknown` with
`reconciliation_required`.

## 6. Fixed execution and health

The runner performs only this sequence:

1. reverify runner, request, staging manifest/archive/Compose hashes;
2. acquire the deployment lock;
3. prepare `releases/<releaseId>` without overwriting a conflicting release;
4. stream the approved `none`, `gzip`, or `zstd` archive through a private FIFO
   into `docker load`;
5. inspect the exact repository/tag and require the approved image ID;
6. generate a runtime-owned Compose override containing only the approved image
   and service scope;
7. run fixed `docker compose config` for the approved project/files;
8. optionally pull, then run `docker compose up -d --no-build --pull never`
   limited to those project/files/services;
9. verify selected services are running and, when configured, poll the bounded
   HTTP check at `http://127.0.0.1<path>` for the approved status;
10. optionally run exactly `nginx -t`, then exactly
    `sudo -n systemctl reload nginx`, then repeat health verification;
11. atomically replace `previous` and `current` release symlinks; and
12. record the terminal result.

The runner never restarts the Docker daemon, never runs a caller-supplied shell
workflow, never accepts Nginx configuration text, never runs Nginx `restart`,
never cleans a published release, and does not implement cross-host or rolling
multi-service deployment.

## 7. Cancellation, automatic restore, and uncertainty

Cancellation first appends local `cancellation_requested` and transitions to
`cancel_requested`; the active worker writes an immutable remote cancel marker.
Before service mutation it may prove `canceled`. Once Compose may have changed
services, cancellation and any later failure must attempt the exact rollback
release frozen in the approval summary.

Automatic restore reuses the same approved Compose project/files/services,
runs fixed `up -d --no-build --pull never` for the retained rollback release,
and repeats bounded health verification. Only a verified restore may report
`rolledBack`; the durable run becomes `failed` for an execution failure or
`canceled` for a user cancellation. If the rollback identity, Compose inputs,
activation, or health cannot be proved, the only valid result is
`stateUnknown` with `reconciliationRequired: true`.

An SSH disconnect is not success or failure. The native runtime reconnects to
read the atomic remote ledger. Exhausted observation, timeout, malformed state,
or loss of a terminal proof persists `state_unknown` and never claims rollback.

## 8. Phase 6 startup recovery boundary

Application startup and deployment-center initialization expose a bounded,
read-only `DeploymentStartupRecoveryResult`. Its candidates contain only run
ID, exact plan ID/digest, one of `in_progress`, `verifying`,
`cancel_requested`, or `state_unknown`, the last durable local event sequence,
and `reconciliationRequired`. Discovery has no SSH, SFTP, runner, transfer,
cleanup, reload, deployment, restore, or retry side effect. An interrupted
`reconciling` operation is projected using the immutable
`reconciliation_started.previousStatus` and its original operation identity so
the same operation can resume after an application crash.

`DeploymentReconciliationRequest` remains frozen: operation ID, exact plan
ID/digest, run ID and expected event revision, the immutable successful
transfer receipt operation ID, and opaque staging identity. It accepts no
command, executable, argument, environment, local path, remote path, health
URL, Compose override, or credential. The runtime validates the exact run,
plan, receipt, and staging bindings, then uses one compare-and-swap transaction
to append `reconciliation_started` and enter `reconciling`. Concurrent,
duplicate-with-a-different-revision, stale, or differently bound requests fail
closed. Repeating the exact completed operation returns its durable result;
resuming an interrupted operation requires the same operation and frozen
bindings.

Reconciliation resolves only the approved profile credential reference and
Known Hosts identity. Its remote protocol is fixed and read-only: it reads the
SHA-256-addressed runner, immutable request, launch marker, atomic status,
contiguous event files, `current`/`previous` links, target and frozen rollback
release digests, and fixed Docker Compose container/image/health evidence. It
does not write a runner request or cancellation marker, launch a process,
change a service, restore a release, clean a release, or reload Nginx. Stopping
observation cancels only the local observation operation and never represents a
deployment cancellation.

Remote events are matched by their remote sequence, phase, fixed action,
outcome, and bounded summary. Already imported local events are immutable and
must byte-for-byte agree with the remote ledger projection. Only a contiguous
missing suffix may be appended. A gap, truncation, reorder, duplicate, unknown
field, changed event, status/sequence disagreement, or unsafe file identity is
an unprovable state.

## 9. Reconciliation decisions

Every completed attempt appends `reconciliation_completed` with the bounded
evidence projection and one of these proved decisions:

- the target release is `current`, its approved digest and Compose image match,
  all approved services are running and health is verified: `succeeded`;
- the exact frozen rollback release is `current`, `previous` is the target,
  its digest, Compose image, services, and health are verified: `failed`, or
  `canceled` when the immutable local ledger contains cancellation intent;
- the fixed runner and contiguous ledger prove it is still executing:
  `in_progress`, `verifying`, or `cancel_requested`, followed by read-only
  observation until a terminal proof, timeout, or user stop;
- the immutable launch marker is absent, or a valid terminal status proves
  `sideEffectsStarted: false`: `approved` only when the exact approval remains
  unexpired and every frozen source/workflow/profile/artifact/receipt input is
  unchanged, otherwise `canceled`; or
- any other result, including missing/tampered evidence, identity mismatch,
  contradictory links, unhealthy or wrong-image containers, profile or host-key
  drift, connection interruption, or timeout: `state_unknown` with
  `reconciliationRequired: true`.

SSH exit status alone is never a deployment result. The runtime requires the
complete, strictly parsed evidence document. An `approved` result may start the
existing RemoteRunner only with the original plan digest, new current run
revision, original receipt and staging identity, and full Phase 5 revalidation.
Expired approval or any changed frozen input requires a new plan and native
approval; the old digest is never modified or implicitly renewed.

## 10. Phase 7 history, navigation, and notifications

The Rust repository remains authoritative for run history. Run pages use a
stable `(created_at, run_id)` cursor. A run detail returns the durable run plus
a bounded latest event window, while older immutable events are loaded with a
strict `before_sequence` page. Frontend progress logs are transient presentation
only and never determine a durable status, active release, failure, or recovery
decision.

Every history row exposes the frozen workflow/environment/target identity,
source revision and dirty state, current/target/rollback releases, durable
status, approval summary, start/end/duration, and bounded event evidence. The
workflow list reports a current release only when the latest durable result
proves the target release succeeded; other outcomes are displayed as unproven
rather than guessed.

Navigation from the command palette, connection list, host quick surfaces,
sidebar attention badge, and cross-workspace recovery notice can only select a
profile, workflow, new-release review surface, or exact run. Those entry points
have no approval or execution command. `state_unknown` and interrupted runs
always route to the recovery card, and effectful actions remain gated. Expired
plans or changed workflow/source/target/artifact identities route to a clean new
plan and never renew or reuse the prior approval. An approved run is resumable
only when Phase 6 produced the exact reusable binding and the approval remains
unexpired and unchanged.

SQLite schema v6 stores immutable notification receipts keyed by run, durable
event sequence, and notification kind. Existing outcomes are backfilled as
already delivered during migration. New notifications are limited to approval
or other required user action, proved success, verified automatic restore, and
failure. In-progress, unchanged, and ordinary cancellation states do not
notify. A receipt is claimed transactionally before presentation, so restart
recovery does not repeat the same durable outcome. Notification content contains
only workflow name, run identity, and a fixed localized outcome; it excludes
credentials, raw logs, commands, host secrets, and event payloads. Native and
in-app activation emit only the selected run identity and route to that exact
run.

## 11. Phase 8 production hardening matrix

Phase 8 must collect real-environment evidence for at least:

| Area | Required production evidence |
| --- | --- |
| SSH transport | Direct and jump-host password/key fixtures, Known Hosts rotation/rejection, disconnects before and after side effects, reconnect exhaustion |
| Remote filesystems | ext4, XFS, and supported network filesystems; atomic rename/link behavior; permission, ownership, disk-full, and inode exhaustion faults |
| Docker/Compose | Supported Engine and Compose versions on amd64/arm64, image-ID mismatch, unhealthy containers, pull/config/up failures, daemon restart during observation |
| Runner ledger | Missing/gapped/reordered/changed events, truncated status/request/launch marker, wrong runner digest, concurrent workflow lock contention |
| Recovery soak | Multi-hour detached runs, repeated application/host restarts, observation stop/resume, timeout boundaries, notification dedupe across restart |
| Rollback drills | Pre-mutation cancel, post-mutation cancel, health failure, Nginx validation/reload failure, verified restore, unprovable restore to `state_unknown` |
| Audit lifecycle | Signed export, retention limits, deletion policy, secret scanning, bounded payload enforcement, operator review procedure |
| Operations | Metrics and alert thresholds, support diagnostics, runbook ownership, backup/restore of repository state, incident and rollback rehearsal |

Phase 8 may not weaken the frozen request, approval digest, fixed runner,
read-only reconciliation, credential isolation, immutable event ledger, or
fail-closed evidence rules. Cross-host rolling release, arbitrary shell, release
cleanup, and automatic approval remain out of scope.

## 12. Phase 8 audit, rollout, and retention policy

The native `export_deployment_run_audit` boundary accepts only one validated
run ID. It reloads that exact durable run and its complete contiguous event
timeline, then produces audit schema v1. The document is capped at 2 MiB and
500 events. It contains a redacted approval projection, ordered status
timeline, allowlisted evidence, terminal result, retention policy, and a
SHA-256 integrity digest. It excludes credentials and credential references,
connection endpoints and usernames, jump-host endpoints, local source paths,
remote roots, the opaque artifact reference, arbitrary event payload fields,
and raw output. Export uses a private temporary file, sync, and atomic publish;
canceling the save dialog writes nothing. Export never appends an event or
changes the run. Signing is explicitly `notConfigured`; a checksum must not be
represented as an operator or organizational signature.

`SHELLSPAN_DEPLOYMENT_CENTER_V1` is the native restart-scoped rollout gate. Its
default is enabled for the Phase 8 MVP. `0`, `false`, `off`, or `disabled`
reject new workflow mutations, builds, preflights, plan creation, approval,
transfer, and runner admission. Invalid values fail closed. Read-only history,
audit export, cancellation, notification projection, startup discovery, and
reconciliation remain available so rollback of the feature cannot strand an
uncertain run. The UI reads this native decision and enters a clearly labeled
read-only recovery mode; it is not the enforcement boundary.

`releasesToKeep` remains validated and frozen for forward compatibility but is
not an execution instruction in Phase 8. No automatic remote release cleanup is
implemented. The runner never deletes a published release and never invokes
recursive deletion. Adding cleanup later requires a new reviewed fixed action,
explicit approval-summary binding, current/previous exclusion, runtime-owned
manifest and release-ID validation, and durable audit evidence.

The Phase 8 archive identity is the SHA-256 digest of the image config selected
for the exact repository/tag in `docker save`'s bounded manifest, not a Docker
Desktop OCI index digest. The config blob is read from the archive and its
digest is verified before publication. This keeps the approved image identity
stable when loading a single-platform artifact from a containerd-backed local
store into an independent Docker daemon.

No SQLite migration or workflow/approval schema increment is introduced by
Phase 8. Disabling the rollout is the first rollback action. A Phase 7 binary
can still read Phase 8 workflows, plans, and manifests because their schemas are
unchanged; it does not know the additive audit/capability commands. Database
downgrade rules remain unchanged and destructive migration rollback remains
forbidden.
