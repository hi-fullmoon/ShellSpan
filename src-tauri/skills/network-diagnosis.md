# Network diagnosis

Diagnose connectivity from the current terminal target and answer in the user's language. Keep commands bounded and within existing permissions. A working directory is unnecessary. Do not change DNS, routes, firewall rules or interfaces as part of diagnosis.

1. Identify the destination, expected protocol/port and observed symptom. Use provided context; ask for a missing destination if the requested connection cannot otherwise be tested.
2. Prefer `diagnose_endpoint` for the explicit destination and port, choosing tcp/tls/http/https to match the request. Report DNS, per-address TCP attempts, verified TLS and HTTP HEAD stages separately; retain vantage point, time and evidence reference. No redirects or proxies are used, and one sampled backend does not prove all addresses work. Use `inspect_host` for platform/capability discovery when needed. Inspect interfaces/routes only with existing authorized platform tools when the endpoint evidence warrants it. If a check is denied, do not change DNS or try another route around the policy.
3. Distinguish DNS failure, missing route, TCP refusal/timeout, TLS error and application response. For HTTP on the frozen local or remote target's loopback interface, use `probe_http` with an explicit method, port, path, short timeout and bounded response size; it cannot follow redirects, use a proxy, or send arbitrary headers. Probe any other endpoint only when another structured tool and the current permission scope authorize that destination. The terminal is not a network sandbox: shell network commands may require external-side-effect approval but cannot provide an exact enforced destination scope. Do not retry a denied request through a wrapper or another interpreter. ICMP failure alone does not prove a host is down.
4. When checking a local service, inspect listening sockets with available tools such as `ss` or `lsof`. Check only relevant destinations and ports; do not scan unrelated networks. Avoid exposing credentials in URLs, headers or diagnostic output.
5. Report where the failure occurs, evidence from both successful and failed checks, and the next targeted action. Quote user-supplied destinations safely when forming arguments.
